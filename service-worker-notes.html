Gmail OTP Catcher — Internal Notes

Service Worker:
Problem, Fix & Future

A plain-English record of the core technical challenge behind the extension — why the overlay only appeared on tab switch, how it was fixed, and what the production-ready path looks like.

Rakshith Reddy  ·  Gmail OTP Catcher v1  ·  February 2026
01

What is the Service Worker?

A Chrome extension is split into two parts. The part you see — the overlay on screen, the popup when you click the icon — lives on the page you're looking at. Then there's the invisible part: the service worker.

The service worker is a background script that runs your code silently. In this extension, its only job is to call Gmail's API every 10 seconds, and when it finds an OTP email, push the code to whatever tab you're on so the overlay appears.

In plain terms Think of it as a person sitting in a back room, watching your inbox, and shouting the code through the wall the moment one arrives. No face. No UI. Just runs code in the background.
02

Why Chrome Puts It to Sleep

Chrome runs on your laptop. Your laptop has limited battery and memory. Chrome is already juggling your tabs, videos, and other extensions. It cannot afford to keep every extension's background worker running forever.

So Chrome has a hard rule:

Chrome's Rule If a service worker has done nothing for ~30 seconds, Chrome shuts it down. Not forever — but it goes completely cold. No code runs. Nothing.

Chrome does keep a separate always-on system that watches for events — things like "user switched tab" or "alarm went off." This tiny listener never sleeps. When an event fires, it wakes the service worker back up.

03

The Problem — Overlay Only on Tab Switch

This was the core user frustration: the overlay was not appearing automatically. It would only appear after switching to a random tab and switching back to the job application page.

Here is exactly what was happening:

  • 1
    User is on Greenhouse / Oracle, filling out a form Service worker is asleep — nothing has happened in 30+ seconds.
  • 2
    User hits Submit — OTP email arrives in Gmail Nobody is checking. The worker is still asleep. Email sits unread.
  • 3
    User switches to a random tab Chrome's always-on event listener fires a "tab switched" event. Worker wakes up, checks Gmail, finds the code, stores it.
  • 4
    User switches back to the job application tab The page asks the worker "do you have anything new?" — worker says yes. Overlay appears.
The core issue The overlay wasn't appearing because the extension detected the email in real time. It appeared because tab-switching accidentally woke up the background worker, which then found the email. The user was unknowingly using tab-switching as a manual on/off switch.
04

The Fix — Persistent Port Connection

Chrome's sleep rule is: "if nobody is talking to the worker, put him to sleep." The fix exploits exactly that rule in reverse. If someone is always talking to the worker, Chrome cannot put him to sleep.

The moment you load any webpage, the content script — the part of the extension that lives on the page — opens a direct private line to the service worker. Like picking up a phone and calling him.

Chrome sees the open call. Chrome cannot shut the worker down. The worker stays alive and runs a reliable loop: check Gmail every 10 seconds, find a code, push it through the open line, overlay appears immediately — no tab switching, no clicking.

What changes with the fix The page holds an open connection (called a "port") to the background worker for as long as the tab is open. Chrome's idle timer never starts because the worker is never considered idle.

Flow — Before the fix:

Gmail email arrives
→
Worker asleep
→
Tab switch (accidental)
→
Worker wakes
→
Switch back
→
Overlay shows

Flow — After the fix:

Gmail email arrives
→
Worker always on
→
Overlay shows instantly

What happens when you close all tabs?

The open line drops. The worker has nobody talking to him, Chrome puts him to sleep. But the moment any new tab loads, a fresh content script picks up the phone again and the worker wakes up immediately.

05

Trade-offs & Disadvantages

Keeping the worker always alive is a workaround, not a perfect solution. There are real costs worth acknowledging.

Does this drain battery or memory?

Yes, slightly. Every open tab holds a port connection. Ten open tabs means ten open connections to the same worker. The worker also makes a Gmail API network call every 10 seconds — small, but constant. For personal use the impact is negligible. At scale with many users, it adds up.

How does this compare to the iPhone OTP approach?

iOS reads an SMS that is already on the device. No network call. No persistent connection. Zero battery cost between messages. The current extension approach requires constant polling — the opposite of that.

Honest assessment The current solution is reliable and works well for personal use. But it is polling-based — the extension is always asking Gmail "anything new?" The production-ready solution would have Gmail tell the extension when something arrives, rather than the extension constantly asking.
06

The Production-Ready Future — Gmail Push Notifications

Instead of the extension asking Gmail every 10 seconds, Gmail itself sends a notification the moment an email arrives. This is called Gmail Push Notifications via Google Cloud Pub/Sub.

Current approach (polling):

Extension
→ asks every 10s →
Gmail API
→
Overlay

Production approach (push):

Gmail
→
Google Pub/Sub
→
Your Server
→
Extension
→
Overlay

With this approach, the worker only wakes up when there is actually something to process. Zero wasted checks. No persistent connection needed. No battery drain between emails.

What needs to be built:

  • A small backend server to receive Gmail's push notifications
  • Google Cloud Pub/Sub topic and subscription set up
  • Gmail's watch() API registered for each user
  • Extension updated to listen for push instead of polling

08

When to Make the Switch

The current polling solution works well for personal use and early testing. There is no need to switch to Pub/Sub immediately. The right time to switch is when:

  • Submitting to the Chrome Web Store for public distribution
  • Real users start depending on it and reliability matters at scale
  • Battery or performance feedback starts coming in
  • Adding Outlook / other providers (server architecture makes multi-provider easier)
Important Switching to Pub/Sub does not require rewriting the extension. The OTP detection logic, overlay, and UI all stay exactly the same. Only the trigger mechanism changes — from polling to push. It is an upgrade, not a rebuild.
